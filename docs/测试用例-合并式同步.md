# 测试用例 — 合并式同步（sync-merge）

> 状态：待评审（评审通过后才进入开发）
> 日期：2026-09-10
> 对应设计：`docs/superpowers/specs/2026-09-10-sync-merge-design.md`

**通用前置**：设备 A、B 已通过同一同步码绑定同一旅行；每条用例标注的「本地」指当前操作设备，「远端」指云端 trips 文档。时间为 ISO 字符串，`t1 < t2 < t3` 表示先后关系。

---

## 一、记录合并矩阵（T-M）

| # | 场景 | 前置 | 步骤 | 预期 |
|---|---|---|---|---|
| T-M01 | 本地新增，远端无 | 双端各有记录 R1 | A 新增 R2（不同步），B 端触发同步 | 同步后远端含 R2；A 的 R1/R2 均保留 |
| T-M02 | 远端新增，本地无 | 同步基线 R1 | B 在远端新增 R3，A 触发同步 | A 获得 R3，A 原有记录不动 |
| T-M03 | 同 id 双端修改，本地新 | 双端同持 R1 | A 改 R1（updatedAt=t2），远端 R1 已被改（updatedAt=t1），A 同步 | 合并结果取 A 的版本（LWW 本地胜），远端更新为 A 版本 |
| T-M04 | 同 id 双端修改，远端新 | 双端同持 R1 | A 改 R1（updatedAt=t1），远端 R1 已被改（updatedAt=t2），A 同步 | 合并结果取远端版本（LWW 远端胜），A 本地被替换 |
| T-M05 | 同 id 双端修改，时间完全相同 | 双端同持 R1，双方 updatedAt 字符串全等 | 触发同步 | 远端版本胜（确定性规则） |
| T-M06 | 本地删除传播 | 双端同持 R1 | A 删除 R1，A 同步 | 远端 R1 移除且墓碑含 R1.id；B 下次同步后 R1 也消失 |
| T-M07 | 远端删除传播 | 双端同持 R1 | B 删除 R1 并同步，A 同步 | A 的 R1 消失 |
| T-M08 | 删除 vs 后编辑，墓碑新 | 双端同持 R1（updatedAt=t1） | A 删除 R1（墓碑 deletedAt=t2）；远端 R1 被改为 updatedAt=t1.5（早于墓碑）；A 同步 | 保持删除（墓碑 deletedAt > 记录 updatedAt） |
| T-M09 | 删除 vs 后编辑，编辑新 | 双端同持 R1（updatedAt=t1） | A 删除 R1（墓碑 deletedAt=t1.5）；远端 R1 被改为 updatedAt=t2（晚于墓碑）；A 同步 | R1 复活且为远端新版本 |
| T-M10 | trip 元数据 LWW | 双端同持基线 | A 改旅行名（metaUpdatedAt=t2），远端也被改名（t1），A 同步 | 名称取 A 版本；反向同理 |
| T-M11 | 元数据时钟碰撞 | 双端 metaUpdatedAt 全等 | 同步 | 远端胜（确定性） |
| T-M12 | 无变化幂等 | 双端一致 | 连续触发同步 2 次 | 数据无变化；revision 不增；每次返回 merged |
| T-M13 | 混合大杂烩 | 见下 | 一次性构造：本地 3 新增 + 2 修改（1 新 1 旧）+ 1 删除；远端 2 新增 + 2 修改（与本地修改部分同 id）+ 1 删除（与本地删除不同 id） | 合并结果逐条符合上述规则，revision 恰好 +1 |

## 二、去重检测（T-D）

四要素 = 支付人 + 受益人集合 + 金额（分） + 项目。受益人**顺序不同**视为相同；note/时间不参与。

| # | 场景 | 前置 | 步骤 | 预期 |
|---|---|---|---|---|
| T-D01 | 本地新增与远端已有重复 | 远端有 R1（成员1 付，全员受益，¥50，正餐） | A 新增 R2（四要素同 R1，不同 id）→ 触发同步 | 阶段 1 返回 duplicates=[{local:R2, remote:R1}]；确认「重复」→ R2 不上云，本地 R2 消失，R1 保留（保留非新到方） |
| T-D02 | 远端新增与本地已有重复 | 本地有 R1 | 远端新增 R3（四要素同 R1），A 同步 | 弹窗确认「重复」→ 远端 R3 加墓碑，本地 R1 保留，最终双端只有 R1 |
| T-D03 | 双端各自新增（不同 id 同要素） | 基线为空 | A 新增 R2（createdAt=t1），远端新增 R3（createdAt=t2），同步并确认「重复」 | 保留 createdAt 早的 R2；R3 墓碑；R2 同步到双端 |
| T-D04 | 双端各自新增，createdAt 相同 | 同上但时间全等 | 同步并确认「重复」 | 保留远端 R3（确定性），R2 不上云 |
| T-D05 | 判定「不重复」 | T-D01 前置 | 弹窗选「保留两条」 | R1、R2 均在双端存在（真实场景：两顿一样的饭） |
| T-D06 | 多条疑似重复 | 远端有 R1、R4（均与新记录同要素） | A 新增 R2 同步 | 逐条弹窗（R2↔R1、R2↔R4）；每条独立裁决 |
| T-D07 | 本地新增即时检测 | 本地已有 R1（≈远端） | A 在表单新增与 R1 同要素的记录并提交 | 提交时即弹窗「与现有记录疑似重复」；确认重复 → 放弃新增（表单数据不清空，用户可改）；不重复 → 正常添加 |
| T-D08 | 本地修改成重复 | 本地有 R1、R2（要素不同） | 把 R2 改成与 R1 四要素相同 | 弹窗提示；确认重复 → 放弃修改，R2 保持原值 |
| T-D09 | 受益人顺序不同 | R1 受益 [m1,m2] | 新增 R2 受益 [m2,m1] 其余同 | 判定为重复（集合比较） |
| T-D10 | 边界不判重 | — | 金额差 1 分 / 项目差一字 / 支付人不同 / 受益人多一人 | 均不判重，正常同步 |
| T-D11 | 已共存记录不再提示 | 双端已同步持 R1、R2（同要素，曾选「保留两条」） | 再次同步 | 不再弹窗（只对新到记录检测） |

## 三、自动同步与状态指示（T-A）

| # | 场景 | 步骤 | 预期 |
|---|---|---|---|
| T-A01 | 新增后自动同步 | A 添加一笔 | 状态 chip：同步中 → 同步成功；远端立即含新记录；无弹窗（无重复时） |
| T-A02 | 修改后自动同步 | A 修改一笔 | 同上，远端更新为修改版 |
| T-A03 | 删除后自动同步 | A 删除一笔 | 远端移除 + 墓碑 |
| T-A04 | 进入/刷新自动同步 | 远端有 A 没有的记录，A 刷新页面 | 页面加载后本地补齐远端记录，状态 同步成功 |
| T-A05 | 快速连续记账 | 1 秒内连续添加 3 笔 | 请求串行（同一时刻 ≤1 个在途）；最终 3 笔全部上云；无重复提交 |
| T-A06 | 未开启同步不触发 | 新设备未绑定 | 添加/刷新 | 无任何同步请求发出，无状态 chip |
| T-A07 | 弹窗时机 | A 新增重复记录 | 自动同步的确认弹窗在记账流程后出现，不阻塞表单提交本身；确认后完成合并 |
| T-A08 | 手动同步按钮 | 点击头部「同 步」 | 执行同一合并流程；与自动同步共用串行队列 |

## 四、弱网与异常（T-N）

| # | 场景 | 模拟方式 | 预期 |
|---|---|---|---|
| T-N01 | 请求超时 | 断网/拦截请求挂起 | 状态 → 同步失败（点击重试）；本地数据完整不动；无崩溃 |
| T-N02 | 失败自动重试 | 断网记账 → 恢复网络后再次记账/刷新 | 恢复后触发成功，之前积压变更一并合并 |
| T-N03 | 同步中断后重发（幂等） | 阶段 1 请求实际到达服务端但响应丢失，客户端重试 | 重发相同 payload，合并幂等：记录不重复、revision 不异常增长 |
| T-N04 | 阶段 1 后断网 | duplicates_found 返回后立即断网，用户已确认部分条目 | 已裁决部分：阶段 2 请求失败 → 状态失败；本地待确认项保留；恢复后重新探测重新弹窗（pendingDecisions 不持久化） |
| T-N05 | 阶段 2 失败重试 | 断言 decisions 请求失败后网络恢复重试 | 裁决生效，最终状态正确 |
| T-N06 | 服务端 5xx | 函数异常 | 状态失败；本地不损坏；下次触发重试 |
| T-N07 | 慢网下的串行 | 第一个请求 10s 未返回期间连续记账 3 次 | 队列 pending 合并：第一个完成后仅补跑一次（共 2 个请求），不堆积 |
| T-N08 | 双端同时同步（TOCTOU 窗口） | A、B 毫秒级间隔同时 POST | 最终远端为两次合并的收敛结果（后写者读到前者结果再合并），无数据丢失；无 409 |

## 五、大数据量差异（T-L）

| # | 场景 | 数据规模 | 预期 |
|---|---|---|---|
| T-L01 | 全量上行 | 本地 200 条（20 成员），远端空 | 单次同步全部上云；响应含全部 200 条；耗时在函数超时（10s）内 |
| T-L02 | 全量下行（新设备） | 远端 200 条，本地 0 条 | 加入旅行 → 拉取完整；页面渲染与结算正常 |
| T-L03 | 大规模双向分歧 | 本地 100 新增 + 50 修改；远端 100 新增（与本地不重叠）+ 50 修改（同 id 交错新旧） | 一次合并全部收敛；每条按 LWW 规则正确裁决；revision +1 |
| T-L04 | 大规模删除 | 远端墓碑 100 条 + 各端同步 | 墓碑并集传播；双端一致剔除 |
| T-L05 | 接近上限 | payload ~500KB（~2000 条记录） | 正常同步；>512KB → 400 PAYLOAD_TOO_LARGE，状态失败且本地不损坏 |
| T-L06 | 大分歧 + 重复风暴 | T-L03 规模中混入 30 对疑似重复 | 阶段 1 返回 30 条 duplicates；逐条裁决后一次阶段 2 收敛 |

## 六、兼容与迁移（T-C）

| # | 场景 | 前置 | 预期 |
|---|---|---|---|
| T-C01 | 云端 v1 文档迁移 | trips 集合中有 v1 文档（无 updatedAt/墓碑，可能是 v1 测试期遗留） | v2 客户端首次同步：backfill 后正常合并，写回 schemaVersion 2 |
| T-C02 | 本地 v1 localStorage 迁移 | 浏览器存在旧版数据（无 updatedAt/deletedIds） | 加载即 backfill；同步行为与 v2 数据一致 |
| T-C03 | 旧版线上 H5 并存 | 线上 H5 仍为 v1 代码（推/拉端点） | v1 客户端推拉正常（旧端点保留）；v2 客户端合并不受影响；两代客户端写入的数据可互相合并 |
| T-C04 | v1 JSON 导入 | 导出文件为旧格式 | 导入成功，记录 backfill updatedAt=createdAt；可正常参与同步 |
| T-C05 | v2 导出/导入闭环 | v2 设备导出 → 新设备导入 → 加入同一码同步 | 数据一致（含墓碑：远端已删记录不复活） |
| T-C06 | 已知限制验证：v1 导入复活 | 远端有墓碑 R1；导入含 R1 的 v1 旧 JSON | R1 复活（无墓碑信息，设计接受的已知限制，文档记录） |
| T-C07 | sync 状态迁移 | 本地存在 v1 sync 状态（含 baseRevision） | 加载后 baseRevision 被丢弃；code/myMemberId/lastSyncedAt 保留；同步正常 |

## 七、回归（T-R）

| # | 场景 | 预期 |
|---|---|---|
| T-R01 | 手动「同 步」按钮 | 合并语义（原 推送/拉取 两按钮已合并删除） |

| T-R06 | 单元测试 | 现有 91 个测试全过（允许行为变更处同步修正：v1 pushTrip/pullTrip 单测改为 v2 客户端单测） |

- **单测（vitest）**：T-M 全部、T-D09~T-D11、合并纯函数矩阵（core.js）+ 客户端解析（sync.js）+ 自动同步队列/状态机（store）

- **手动/脚本**：T-L05~T-L06
